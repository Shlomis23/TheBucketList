# The Bucket List — תוכנית ביצוע (Execution Plan)

**מבוסס על:** `The-Bucket-List-Technical-Spec-HE.md` (גרסה 1.0, 24.9.2026), ובפרט על הפרומפט בסעיף 17.
**מטרת המסמך:** לתרגם את הפרומפט ואת האפיון המלא לתוכנית ביצוע מסודרת, לפי שלבים, עם קריטריוני יציאה ובדיקות. **מסמך זה הוא תכנון בלבד — לא בוצע בו שום שינוי קוד, סכמה או תשתית.**

---

## 0. מצב מוצא

- בתיקייה `TheBucketList` קיים כרגע רק קובץ האפיון עצמו. **אין עדיין repo, קוד או migrations שהורצו.** לכן ההנחיה בפרומפט "בדוק את מצב הריפו, ואם קיים שמור על שינויים" רלוונטית רק אם ה-repo ייווצר/יחובר במקום אחר — יש לוודא זאת בפועל לפני תחילת שלב 0.
- ה-SQL, ה-RPC וההרשאות במסמך הם **בסיס שלא נבדק בהרצה** (סעיפים 10.1, 14.3) — התוכנית מטפלת בהם ככאלה: צריך migrations אמיתיות + בדיקות, לא העתקה ישירה.
- כל מחיר/תאריך/שם ספק במסמך הם דוגמאות בלבד; אין להביא נתונים אמיתיים ל-production (סעיף 1).

## 2. הזרימה האנכית הראשונה (מה שהפרומפט מבקש לבנות קודם)

לפי סעיף 17: **כניסה → יצירת מרחב → הזמנת בן זוג → רעיון ראשון.**

זו לא "משימה" נפרדת אלא חיתוך אנכי דרך שלבים 0–2 של ה-Roadmap: מספיק Auth+schema+RLS (שלב 0) כדי לבנות onboarding+invite (שלב 1), ומספיק מזה כדי להוסיף את מסך המאגר ותפיסת רעיון ראשונה (חלק משלב 2). התוכנית למטה שומרת על הסדר הזה בפועל, לא רק בתיאוריה.

## 3. שלבי הביצוע

### שלב 0 — יסודות

**מטרה:** תשתית שעליה כל השאר נשען: repo, סביבות, Auth, סכמה, RLS, דפוס RPC.

| משימה | פרטים |
|---|---|
| בדיקת מצב repo | לוודא אם קיים repo קיים; אם כן — לא לדרוס שינויים קיימים |
| שלד פרויקט | Next.js App Router + TypeScript strict, מבנה תיקיות לפי 9.2 |
| סביבות | local/staging/production נפרדות, `.env.example` עם placeholders בלבד, אין `NEXT_PUBLIC_` לסוד (9.3) |
| נעילת גרסאות | בחירת גרסאות stable תואמות + lockfile (9.1) |
| Supabase clients | client נפרד לדפדפן ולשרת, אימות JWT בשרת (`getClaims`/`getUser`) לפי תיעוד עדכני (9.1) |
| DAL | שכבת `server-only`, Zod (או שקול) לכל קלט |
| Migration 001 | סכמה מלאה מ-10.1 — כטיוטת migration, **לא הרצה עיוורת**; לעבור סעיף־סעיף מול הדרישות |
| RLS + helper functions | `is_member`, `can_read_profile`, `list_my_matches` מ-10.2; `REVOKE`/`GRANT` מדויקים; בדיקת grants בפועל אחרי migration |
| Auth redirect allowlist | דומיינים מדויקים בלבד, כתובות חזרה פנימיות (9.1) |
| שלד ניווט/RTL | ניווט תחתון, `lang="he" dir="rtl"`, מסכי empty/loading/error גנריים (סעיף 4, 6) |

**שער יציאה (מהמסמך):** בדיקות בידוד שני מרחבים (שני משתמשים לא רואים זה את זה) + build עובר.
**בדיקות תומכות:** 14.2 #3 (anon/authenticated לא יכולים DML ישיר), חלק מ-#1.

### שלב 1 — מרחב זוגי

**מטרה:** onboarding, הזמנה, קבלה, הגדרות, מצב המתנה, סגירת מרחב (המסלול, לא בהכרח ה-worker המלא).

| משימה | פרטים |
|---|---|
| F1 — יצירת מרחב | `createSpace` (requestId+timezone, space+slot1+mutation key בטרנזקציה אחת) |
| F1 — הזמנה | `createInvitation`: נעילת מרחב, חבר יחיד, ביטול pending קודמת, token CSPRNG 32+ bytes, רק hash נשמר |
| הגנת הזמנה | fragment `#token=`, ניקוי מיידי מה-URL, cookie זמני חתום/מוצפן/HttpOnly, `Referrer-Policy: no-referrer`, אין logging של token (11.2) |
| Rate limiting | 5 הנפקות/שעה למשתמש, 20 ניסיונות בדיקה/15 דק' ל-IP — מבוזר, לא בזיכרון תהליך (11.2) |
| F2 — קבלה | `POST /api/invitations/exchange` (ללא קבלה) → `acceptInvitation` דרך RPC מ-10.3 בדיוק; GET אף פעם לא מקבל |
| מסך הזמנה | `/invite`: הסכמה מפורשת, הודעת שגיאה אחידה לטוקן לא תקין/פג/מבוטל, בלי לחשוף אימייל מלא |
| הגדרות | שם שלי/בן זוג, ניהול הזמנה (ביטול), יציאה |
| F8 — סגירת מרחב (המנגנון, לא ה-worker) | הסבר + אישור מפורש → `closed`, חסימת גישה לשני הצדדים |

**שער יציאה:** מירוצי קבלה (concurrent accept) ואימייל שגוי נבדקו.
**בדיקות תומכות:** AC01, AC02; 14.2 #5 (קבלה מקבילה, שני מרחבים לאותו חשבון), #6 (הזמנה פגה/מבוטלת/token אקראי/אימייל לא מאומת), #10 (redirect זדוני, CSRF, rate limit).

### שלב 2 — מאגר

**מטרה:** בית בסיסי, רעיונות, הוספה מהירה, חיפוש, תגובות אישיות וטקסט, מאצ'ים.

| משימה | פרטים |
|---|---|
| בית `/` | תוכנית קרובה, ספירת מאצ'ים/רעיונות, מצב המתנה לבן זוג (`getHome`) |
| F3 — הוספה מהירה | כותרת חובה בלבד → שמירה → "הוסף פרטים" להרחבה; אין `yes` אוטומטי |
| מאגר `/ideas` | חיפוש (`ILIKE` מוגבל למרחב), פילטר קטגוריה/מאצ'ים/תגובה שלי, cursor pagination (20/עמוד, סדר `(created_at,id)`) |
| עריכה/ארכוב | `updateIdea`, `archiveIdea`/`restoreIdea` — חסימת ארכוב כשקיימת תוכנית `proposed` |
| F4 — תגובה ומאצ' | `setReaction`: upsert/delete רק ל-actor; מאצ' מחושב **רק** דרך `list_my_matches`; אין חשיפת raw reaction של האחר בשום נתיב (כולל joins) |
| תגובות טקסט | `addComment`/`editComment`/`deleteComment` — נפרד לחלוטין מרצון אישי |

**שער יציאה:** זרימה של שני משתמשים עובדת ללא דליפה.
**בדיקות תומכות:** AC03, AC04, AC05; 14.2 #1 (A לא קורא תוכן של C/D), #2 (A לא קורא raw reaction של B בשום צורה כולל REST/join/RPC).

### שלב 3 — בחירה ותכנון

**מטרה:** מנוע בחירה (סעיף 8), תוכנית, גרסאות, אישורים, ביטול.

| משימה | פרטים |
|---|---|
| מנוע בחירה | קלט: `scope`, תקציב/משך/קטגוריה/מיקום, `allowUnknown`, `excludedIdeaIds`; אלגוריתם 8.2 בדיוק (כולל: לא לקרוא תגובות פרטיות ב-`scope=all`, סינון רעיונות עם תוכנית `proposed`, ניקוד, הסבר עובדתי) |
| F5 — מסך בחירה | "עוד הצעה" מדלג על IDs שהוצגו; אין יצירת תוכנית אוטומטית |
| F6 — יצירת תוכנית | `createPlan`: snapshot כותרת, unique תוכנית פעילה per idea |
| עדכון/אישור | `updatePlan` (גרסה+1, מבטל אישורים קודמים), `confirmPlan` (רק כש-`startsAt` קיים, שני אישורים ל-version הנעולה), `unconfirmPlan`, `cancelPlan` |
| Concurrency | `expectedVersion` בכל כתיבה, `409 VERSION_CONFLICT`, UI מציג גרסה חדשה ומאפשר להחיל שינוי מחדש — **בלי מיזוג שקט** |

**שער יציאה:** תרחישי empty/conflict ואישורים נבדקו.
**בדיקות תומכות:** AC06, AC07, AC08, AC09.

### שלב 4 — זיכרונות ו-PWA

**מטרה:** השלמה, ארכיון, תמונות פרטיות, manifest/offline, worker ניקוי ומחיקה.

| משימה | פרטים |
|---|---|
| F7 — השלמה | `completePlan`: מעבר ל-`completed` + יצירת memory באותה טרנזקציה, idempotent (unique על `memories.plan_id`), מותר גם בלי שני אישורים |
| העלאת תמונה | זרימה מלאה מ-11.3: `createPhotoUpload` → upload עם בדיקת origin/session, מגבלת 10MiB לפני buffering, אימות magic bytes + מגבלת פיקסלים, הסרת EXIF/GPS/שם קובץ, `finalize` עם בדיקה חוזרת → `ready` |
| צפייה בתמונה | `/api/photos/[id]/content`: אימות+חברות+ready בכל בקשה, `no-store`, בלי public URL |
| מחיקת תמונה | `deleting` → מחיקת Storage → מחיקת metadata; worker לניקוי orphans/pending ישנים אחרי שעה |
| ארכיון `/memories` | ציר זמן, גלריה, חיפוש |
| PWA | manifest (192/512+maskable), Service Worker לקבצים סטטיים+offline shell בלבד; Auth/invite/API/HTML עם נתוני משתמש ותמונות — network-only |
| סגירת מרחב + מחיקת חשבון (מלא) | `closeSpace`/`requestAccountDeletion`: אימות מחדש, worker תפעולי עם retries, enqueue purge — **לא כחלק מבקשת UI קצרה** |

**שער יציאה:** E2E מלא, בידוד Storage, מחיקה ו-PWA.
**בדיקות תומכות:** AC10–AC15; 14.2 #7 (תמונות: URL ישיר בלי JWT, נתיב מזויף, metadata pending, קובץ מפוברק, EXIF GPS, העלאה בזמן סגירה), #8 (סגירה מתחרה עם כתיבה), #9 (יציאה לא משאירה תוכן שמור בדיסק), #11 (cache/CDN/image optimizer לא מחזירים תמונה בין חשבונות), #12 (restore מגיבוי בסביבה מבודדת).

## 6. גבולות ואזהרות שחוזרות מהמסמך (לא לשכוח בזמן ביצוע)

- אין לכתוב endpoint גנרי עם service role; כל writes דרך RPC צרות בלבד (9.1, 17.4).
- אין להבטיח מחיקה מיידית מגיבויים, ואין לכנות את המוצר "מוצפן מקצה לקצה" — אין E2EE ב-MVP (11.4).
- SQL שבמסמך לא הורץ מעולם — כל migration/RPC חייבים להיכתב ולהיבדק מחדש, לא "להעתיק ולהניח שעובד" (10.1, 14.3, 17).
- אין לפרסם ל-production ואין לשלוח הזמנות אמיתיות בלי הוראה מפורשת של Besti (סעיף 17, שורה אחרונה).
- בסיום כל שלב: לדווח מה הושלם בפועל, אילו בדיקות רצו בפועל, ומה עדיין פער — לא להצהיר "עובד" בלי הרצה.

## 7. הצעד המיידי הבא (לפני כתיבת שורת קוד אחת)

1. לאשר מול Besti את 5 הפריטים בסעיף 1 (ספק אירוח, Supabase, ספק מייל) ואת החלטה #4 וסעיף 5 מטבלת סעיף 5 לפחות.
2. לוודא שאין repo קיים במקום אחר שצריך להתחבר אליו (הנחיית "אל תדרוס שינויים קיימים" בפרומפט).
3. עם אישור — להתחיל שלב 0: שלד Next.js, סביבות, ו-migration 001 כטיוטה לסקירה (לא הרצה על production).
4. רק אחרי ששלב 0 עבר את שער היציאה שלו (בידוד שני מרחבים + build) — לעבור לזרימה האנכית הראשונה (שלב 1 + חלק משלב 2).

**סטטוס נוכחי: לא בוצע אף שינוי קוד/תשתית. זו תוכנית בלבד, ממתינה לאישור.**
